# tdd 与 blast-radius

修复有一条便宜、清楚的本地测试路径时，先把坏掉的行为写成会失败的检查，再改产品代码。改动在 diff 之外还可能碰坏什么时，找出它之所以还能算安全的那一个事实，并用运行中的代码证明，而不是交回一篇听起来像样的说明。

## tdd {#skill-tdd}

原文：{{src:skills/tdd/SKILL.md}} {{src:docs/guide/05-build-and-clean.md}} {{src:docs/guide/10-recipes-and-pitfalls.md}} {{src:skills/poteto-mode/playbooks/bug-fix.md}}

> 修复缺陷且测试路径清楚、便宜时，先让回归测试在修复前失败、修复后通过。路径不实际时不要硬凑测试。

### 何时使用

用户明确要求 TDD、一条会失败的测试或一条回归测试时使用。缺陷本身有明显、便宜的本地测试目标时也使用。测试路径不清楚、昂贵、偏集成，或没有人要求时，跳过。

`name` 是 `tdd`。前置信息含 `disable-model-invocation: true`。正文没有定义这项。

README 的技能表写明：正在修缺陷，并且有便宜的本地测试路径。指南 {{src:docs/guide/05-build-and-clean.md}} 写明，这时整句提示可以只有两个词。

### 运作方式

目标是一条聚焦的回归测试。它在改产品代码之前失败，在修复之后通过。测试编码的是预期行为，不是当前实现的镜像。

不实际的测试不要硬做。现成测试若需要大范围的装置、脆弱的 mock、慢的端到端设施、只有生产环境才有的状态、含糊的复现步骤，或大量无关的夹具变动，就不要新加测试，改用最接近的有用检查。

1. **弄清缺陷。** 写下预期行为、当前行为、受影响的路径，以及最小的可观察复现。
2. **选最窄的可执行检查。** 优先用这条代码路径上已经在用的、最接近的单元、组件、集成或回归测试。看不出实际的测试路径时，不要为了走完流程而从零造一条。
3. **先写会失败的测试。** 加上本来就能抓住这个缺陷的、最小的聚焦测试。它编码预期行为，不镜像当前实现。
4. **修复前先跑这条新测试。** 确认它因预期的原因失败。它若通过，或因无关原因失败，先改正测试或复现，再改实现。
5. **修复缺陷。** 做满足预期行为的最小产品改动，并保住附近的契约。
6. **重跑回归测试。** 确认它现在通过。

会失败的测试不实际时，改用最接近的可执行回归检查。可以是有目标的脚本、手工复现命令、浏览器自动化、快照比较、日志断言，或聚焦的集成检查。

没有新测试，好过一条坏测试。坏测试大多在测 mock，编码的是当前实现细节，依赖时序或无关的全局状态，为一处小修复去搭昂贵设施，或者刚证明完修复就会被删掉。

回复要交证据，不只交结果。

- 点名修复前失败的那条测试或可执行检查，以及它产生的失败。
- 点名修复后通过的那次测试运行，以及附近做过的检查。
- 若修复前的失败证据没法演示，说明原因，并描述改用的最接近回归检查。

### 使用例

下面两条来自原文，不是本书自拟。

README 的例子是：

```text
/tdd implement
```

指南写明，有上下文时这就够了。技能会写最小的、因预期原因失败的测试，然后写修复，再重跑。测试若需要大范围装置或脆弱的 mock，技能会说明，并改用最接近的可执行检查。真实命令已经是更强的证据时，不要硬凑测试。

配方页 {{src:docs/guide/10-recipes-and-pitfalls.md}} 的例子是：

```text
/poteto-mode repro the duplicate write first. if there's a cheap test path, /tdd it. then fix and rerun.
```

同一页写明，用脆弱的 mock 硬凑测试，比跑真实命令证明得更少，剧本允许这么说。

### 陷阱与注意

- 不要为了迁就错误实现而去改测试。
- 不要放宽已有断言，除非预期行为确实变了，而且理由清楚。
- 回归测试盯住这个缺陷。避免大范围夹具变动，也避免顺手扩大无关覆盖。
- 缺陷若是不稳定的，尽量把测试做成确定的，并写明锁住的是哪一个信号。
- 缺陷若暴露出一整类失败，先落地这条聚焦的回归路径，再考虑兄弟覆盖。
- [Bug fix](playbooks-work.md#playbook-bug-fix) 第 5 步采用这套先失败后修复的节奏，条件同样是廉价的本地测试路径。测试昂贵、偏集成或路径不清楚时跳过。该步把失败测试在下、修复在上，称为 [principle-sequence-verifiable-units](principles.md#skill-principle-sequence-verifiable-units) 的典型形状。

### 相关技能

- [blast-radius](#skill-blast-radius)。小 diff 仍不放心它在别处的影响时，直接检查波及范围。本技能没有点名它。
- [Bug fix](playbooks-work.md#playbook-bug-fix)。第 5 步在廉价路径上调用本技能。
- [principle-sequence-verifiable-units](principles.md#skill-principle-sequence-verifiable-units)。原则正文把失败测试在下、修复在上写成交付顺序。

## blast-radius {#skill-blast-radius}

原文：{{src:skills/blast-radius/SKILL.md}} {{src:docs/guide/06-verify-and-ship.md}}

> 在交付前找出一处改动会在别处碰坏什么。列出调用方不是这份工作。工作是找出搜索看不到的破坏，并用运行代码证明它之所以安全的那一个事实。

### 何时使用

说法包括 “blast radius of X”、“what could this break”，以及审查一份你还不信任的小 diff。

`name` 是 `blast-radius`。前置信息含 `disable-model-invocation: true`。正文没有定义这项。

它是 `how` 和 `why` 的同伴。`how` 说明代码做什么。`why` 说明它为什么是这个形状。本技能说明它会在别处碰坏什么。

指南 {{src:docs/guide/06-verify-and-ship.md}} 把一份你并不完全信任的小 diff 交给 `/blast-radius`。它挑出改动之所以安全的那一个事实，靠运行代码证明，而不是写一篇议论。

README 里“模式会替你运行”的那一份清单没有列入本技能。需要时直接调用。

### 运作方式

代理一秒钟就能 grep 到调用方。听起来对的说明一文不值，因为它无论真假都同样令人信服。不要把说明交回去。找出整件事依赖的一两个事实，靠运行代码证明它们。

对安全所依赖的每个事实，在便宜的前提下尽量往下走，并说明停在哪一级。

1. 你这么说。单独这一点没有价值。
2. 你指向那一行。真实的 `file:line`，或库自己的源码。
3. 你表明坏情况到不了。你逐步走过失败路径，它到不了。
4. 你跑了它。脚本或测试调用真实代码，你若错了它就大声失败。
5. 你在运行中的应用里复现了它。

第 4 级通常是一个小脚本。它导入应用实际交付的同一个库，并调用你担心的那一个函数。

步骤：

1. **读改动。** 读 diff，读它增加、修改和删除的符号，读它现在有什么不同，包括 diff 没有写明的那一部分。用 `why` 的第 2 步拉取 PR 和提交。
2. **找出它之所以安全的那一个事实。** 多数看起来危险的改动，安全只因为一个事实，例如 “this call only drops already-dead cache entries and does nothing else”。找出这个事实。它若成立，多数危险情况一次就清掉。时间花在这里，不要花在一长串也许上。
3. **看 grep 停下来的地方。** 读你所调用的库的源码，核对它钉住的版本和任何本地补丁。弄清事情何时运行：微任务、卸载与拆卸、`Solid` 与 `React`。跟着符号搜索会漏掉的东西：API 返回的 JSON、数据库列、线上格式、另一种语言在读同一批字节、功能开关、下游三跳之外的代码。
4. **对每项风险诚实。** 给它一个真实的发生机会，以及发生后的真实代价。保留你确认过的风险。把检查过并排除的另列。规则与 `why` 相同。引用真实的 `file:line`。一次什么都找不到的搜索仍然是答案。不要编造调用方或 API。
5. **证明那一个事实。** 写一个运行真实代码的脚本或测试，跑它，并贴出发生了什么。
6. **大或宽的改动，当成 `arena` 来跑。** 让几个模型回答同一个问题，再合并答案。不同模型抓到的真实缺陷不同。

交回这些：

- **它做什么。** 改了什么，包括不明显的那一部分。
- **它之所以安全的那一个事实。** 陈述它，说明走到了上面的哪一级，并给出证明。证明不了就写 unproven。
- **风险。** 每一项写明怎么坏、`file:line`、多可能、多严重、怎么检查。要紧的那些贴出证明。
- **已排除。** 你检查了什么，以及为什么没事。
- **合并之前。** 能抓住真实缺陷的、最便宜的测试或复现，包括你写的脚本。

文字经过 `unslop`。引用真实代码。拿到任何公开场合之前，去掉私密内容。

回复就是上面这份说明。那一个安全事实要么已证明，要么标成 unproven。

### 使用例

原文给出的触发说法是 “blast radius of X”、“what could this break”，以及审查一份你还不信任的小 diff。技能表的英文是：一份看起来很小的改动，你想知道它还会碰坏什么，并且那个“它之所以安全”的事实是跑出来的，不是断言出来的。

> **示例（本书作者所写，原文中没有）**
>
> `/blast-radius` 这份 diff 只改了缓存淘汰。我还不放心它还会碰坏什么。

按原文，接下来应读 diff 和符号，找出那一个安全事实，到 grep 停下来的地方去看，用脚本或测试跑真实代码，再按交回格式写明证明或 unproven。本书不编造这次检查的结论。

### 陷阱与注意

- 调用方清单不是交付物。
- 听起来正确的说明，无论真假都同样令人信服。停在第 1 级等于没有证明。
- 证明不了就写 unproven，不要把未跑的推理写成已跑。
- 搜索没有命中仍然要报告。不要编造调用方或 API。
- 大或宽的改动不要只靠一个模型。按第 6 步走 `arena`。
