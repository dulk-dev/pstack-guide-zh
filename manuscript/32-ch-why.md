# why：为什么是这个形状

`/why` 调查代码背后的动机和意图。它是 [`how`](how.md#skill-how) 的同伴。`how` 回答代码做什么、怎样运转。`why` 回答哪些力量把它做成了现在的形状。代码本身不携带动机。动机活在提交、PR、票据、文档和对话里。这些材料都不完整，有偏向，有时根本没有。把猜测说成确定，会误导后面的改动。{{src:skills/why/SKILL.md}} {{src:skills/why/references/epistemics.md}}

README 写明，它在运行时发现可用的 MCP，并按证据类别并行查询。类别是源码管理、问题跟踪、长文档、实时聊天、基础设施可观测性、错误跟踪，以及产品分析仓库。{{src:README.md}}

## why {#skill-why}

> 以谨慎、精确的调查者查代码为什么长成这样，把直接证据、推断和空白分开，并给出来源。

### 何时使用

触发说法是 “why does X work this way”、“why we picked Y”，以及设计理由、回归、事后回顾，或有数据支撑的阈值。运行时行为用 `how`。

README 的例子是功能旗标为什么还没打开。指南的例子是重试上限为什么设成五，以及这个理由现在是否还成立。指南把它比作冷案侦探。它从源码管理出发，再并行查询当前 MCP 暴露出来的证据类别。报告引用一切，把直接证据和推断分开。记录稀薄时说 “appears to”。空结果也要报告，因为 “没有人写下为什么” 本身就是一个答案。{{src:docs/guide/03-understand.md}}

前置信息写着 `name: why` 与 `disable-model-invocation: true`。技能正文没有解释后一项。

### 运作方式

姿态是谨慎、小心、精确的调查者。诚实区分知道的和推断的。综合者必须遵守 `references/epistemics.md`。呈现时可以轻改措辞或补上对话上下文，不要改写信心用语。

每一次派出都点名 `pstack-models.mdc` 里的一行角色和一个默认值。`model` 设成那一行的值。规则或那一行缺失时用默认值。值是 `auto` 或 `inherit-parent` 时不设 `model`。Task 拒绝某个 slug 时改用默认值并说明。默认值也被拒绝时，从错误信息里取同一模型族里最接近的有效 slug。

#### 信心层级

最终输出里的每一条主张都必须落在下面五层之一。层级决定它进哪一节，以及怎么说。

1. Direct。有明确的文字引用，而且这段文字回答了问题。不是 “代码做了 X，所以作者一定想要 X”。是作者写下了为什么。例如 PR 描述写明修的是超过 1000 项就无法分页的缺陷。票据写明是客户 Acme 在安全评审里要求的。代码注释写明钳到 100 是因为上游 API 拒绝更大的值。设计文档写明选 A 不选 B 是因为重启后要保留。作者在聊天里说改用这个做法，因为旧的在测试里不稳定。说法用现在时，并紧挨引用。“This exists because X.”
2. Supported。没有单一来源直接说出，但多条间接证据汇合，使它很可能。例如 PR 标题说改善性能，票据标了 `perf`，周围的提交都碰同一条热路径。或者说同一周的其他 PR 都在描述里提到同一次事故。说法要自信，同时标明是推导出来的。“The evidence points strongly to X”，并引用多条来源。
3. Inferred。对上下文的一种合理读法，没有东西明确支持。读者应明白这是解释，不是记录里的事实。例如 PR 没写为什么，但错误当时在生产里发生，而且当天就合并了，于是它像一次热修。说法要留余地：appears、likely、suggests、is consistent with、one reading is。把推断链写出来。“Given A and B, C seems likely because D.”
4. Speculative。一个说得通的假设，证据很薄，其他解释也同样合适。值得摆出来，但要标明是猜测。通常放在 Competing Hypotheses，和其他可能性并排。说法是 “One possibility is X, but we have no direct evidence.”
5. Unknown。找过了，没找到。这是有效而且重要的结果。写清楚搜了什么。 “We searched X, Y, and Z and found no evidence of why.” 比 “We couldn't find out” 有用。

带着信心的词只用于 Direct 或 Supported，而且旁边要有引用：because、the reason is、was designed to、fixes、addresses、solves、the team decided。推断用 appears to、seems to、likely、suggests、is consistent with、one reading is、plausibly、may have been、the evidence points toward。避开 obviously、clearly、of course，以及把事情说成 “it's just X” 的 just。不用 “I think” 或 “I believe”。你在综合证据，用 “the evidence suggests”。

今天说得通的代码，写它的理由可能已经不适用，或者当初就是错的。不要把整齐的理由倒填回混乱的历史。不要假定作者做了 “对的事” 再倒推。不要把代码库里一致的模式当成有意为之，它可能是复制粘贴。不要把没有证据当成证据的反面。没有人提到安全，不等于安全当时不是问题。

用户常把假设嵌进问题里，例如 “为什么这样做，我猜是为了性能”。把它当成待查的候选，独立核对证据。证据支持就带引用说支持。不支持就说不支持，并给出证据实际支持的内容。用户的猜测是调查的起点，不是要去证实的结论。

两个来源不一致时，两个都摆出来。票据说是客户的合规要求，PR 说是清理技术债。两者可能都真，也可能有一个错。把引用交给用户判断。

诚实的 “我们不知道” 很有价值。用户于是知道答案不在显眼的地方，需要去问人，或者这个问题不值得再追。用自信的猜测填上缺口，用户会按猜测行动。缺口要写明想回答的问题、搜了哪些来源、在每个来源里搜了什么、找到了什么。

交卷前，综合者复查 What We Found 和 What We Can Reasonably Infer 里的每一条。没有引用的，补上引用，或移到推断或假设。措辞要和层级相称。Direct 可以说 because。Inferred 不能。代码本身不能当作自己意图的证据。没有 What We Don't Know，就值得怀疑。要么证据异常完整，要么有东西被扫到地毯下面。

#### 第 1 步，弄清目标和问题

目标通常是一块代码、一种模式、一个功能，或一个点名的设计决定。问题通常是设计理由、取舍、促成它的边界情况、外部约束、死代码，或一次宽泛的历史扫查。

目标含糊时，例如只说 “为什么我们这样做” 而没有明确对象，就从对话上下文做最好的猜测。打开的文件、最近的编辑、光标位置、刚才在谈的内容，都可以用。简短说出你的理解，以便用户改口，然后继续。

#### 第 2 步，先钉住代码锚点

派出调查员之前，先把调查锚在具体代码上。需要这些东西。

- 相关文件路径和行范围
- 关键符号，包括函数名、类名、常量
- 一份初始提交列表，也就是最近碰到目标的若干次提交
- 从合并提交主题里用模式 `(#1234)` 抽出的 PR 号

在当前上下文里直接做。

```bash
git blame -L <start>,<end> <file>
git log --follow -p -- <file>
git log --oneline -20 -- <file>
git log -1 --format=%B <commit>
```

对有实质内容的提交，用 `gh` 拉取 PR 正文和讨论。

```bash
gh pr view <number> --json title,body,author,createdAt,mergedAt,labels,closingIssuesReferences,comments,reviews
```

把这些收成种子上下文：文件路径、符号、提交、PR 号、链接到的票据 ID。传给调查员。

#### 第 3 步，并行派出调查员

默认做完整的并行调查。

派出之前，先列出 Cursor 环境里可用的 MCP。有可用工具地图就用它。否则查看 Cursor 为已启用 MCP 服务器暴露的 `mcps/` 目录。

把每个可用 MCP 归到一个证据类别。

1. 源码管理历史
2. 问题或票据跟踪
3. 长文档
4. 团队实时聊天
5. 基础设施可观测性
6. 错误或异常跟踪
7. 产品分析仓库

源码管理始终可通过 git 和 `gh` 使用。其余六类按 MCP 的名字、服务器说明、工具名和资源描述来归类。一个 MCP 可能跨两类时，选它的主要证据所在的那一类。含糊的情况记在覆盖图里。

目标是一张完整的覆盖图，不是一张最小的图。空也要记下来，不要跳过搜索。

在同一条消息里启动所有匹配的调查员，让它们并发。不要让一个代理覆盖多个 MCP。

每个调查员的配置如下。

- `subagent_type` 为 `generalPurpose`
- `model` 读 `why investigators` 那一行，默认 `grok-4.7-xhigh-fast`
- `readonly` 为 `false`，也就是 `agent` 模式。不要用只读或 `Ask` 模式。那会剥掉 MCP，依赖 MCP 的调查员就整个无法工作。调查员仍然不应该写入任何东西。

每个调查员拿到五样东西。

1. `references/investigator-prompt.md` 里的基础提示
2. 所选 MCP 对应的 `references/sources/<source>.md`。这些文件是例子，按 `references/source-playbook.md` 的索引改写成当前 MCP 的用法
3. 若目标代码看起来是防御性的，再附上横切的 `references/sources/incident-postmortem.md`。防御性指空值检查、重试、超时、限流、功能旗标、出口守卫、`OOM` 处理
4. 第 2 步的代码锚点
5. 用户原来的问题

有匹配 MCP 的类别各派一个调查员。每个只拥有一个工具或一个 MCP。下面每一条点明这类证据独自能露出的 “为什么”。用它来知道该期待什么、某类返回空时怎样命名缺口，以及只在极少、可以证明无关的情况下怎样说明跳过。

1. 源码管理调查员。Git 历史、用 `gh` 看 PR、代码注释、测试。始终派出。这是唯一保证有的来源。最擅长露出评审期间记下的实现时理由。
2. 问题或票据跟踪调查员。例如 Linear、Jira、GitHub Issues、Plane、Shortcut 的 MCP。最擅长露出产品或业务上的迫使力量。为什么在工程之外时最强。
3. 长文档调查员。例如 Notion、Confluence、Google Docs、Coda 的 MCP。最擅长露出长篇设计理由。为什么在变成代码之前被写下来的地方。
4. 团队实时聊天调查员。例如 Slack、Discord、Microsoft Teams、Mattermost 的 MCP。最擅长露出从未写进文档的实时权衡。源码管理、票据和文档的纸面痕迹很薄时尤其重要。
5. 基础设施可观测性调查员。例如 Datadog、New Relic、Honeycomb、Grafana、Splunk 的 MCP。基础设施和运行时的视图。最擅长露出发动这段代码的运行时现实。目标在对基础设施信号作出反应时最强，例如超时、重试、限流、熔断。
6. 错误或异常跟踪调查员。例如 Sentry、Rollbar、Bugsnag、Airbrake 的 MCP。最擅长露出推动防御性或纠正性代码的具体异常和错误轨迹。对 catch、空值守卫、类型检查、重试和其他防御最强。
7. 产品分析仓库调查员。例如 Databricks、Snowflake、BigQuery、ClickHouse、dbt、Redshift 的 MCP。产品和数据的视图。最擅长露出塑造代码的产品和数据现实。对旗标后面的代码、实验驱动的发布、数据迁移，以及 “这个数字从哪来” 最强。

索引和每类说明的对应关系如下。说明文件是常见 MCP 的具体例子。同一类里换一个 MCP，就改写那份说明，不要让一个调查员读多份。

| 类别 | 说明文件 | 例子 |
| --- | --- | --- |
| 源码管理历史 | `code-archaeology.md` | git、`gh` |
| 问题或票据跟踪 | `linear.md` | Linear |
| 长文档 | `notion.md` | Notion |
| 团队实时聊天 | `slack.md` | Slack |
| 基础设施可观测性 | `datadog.md` | Datadog |
| 错误或异常跟踪 | `sentry.md` | Sentry |
| 产品分析仓库 | `databricks.md` | Databricks SQL |

只有两种理由可以跳过一个调查员。跳过必须有写成文字的理由，放进最终的 Sources Consulted。

- 这个环境里该类没有 MCP。这是缺口，不是选择。例如实时聊天被跳过，是因为没有匹配的 MCP，对话记录无法搜索。
- 来源可以被证明无关，而不是 “大概无关”。门槛很高。例如错误跟踪被跳过，是因为目标是构建期脚本，没有运行时代码路径。

若范围判断认为这是一次单提交的琐碎目标，而且 PR 描述里已经有完整答案，可以在行内回答。前提是先确认全部七类可用搜索都是多余的，并把这一点明确说出来。这种情况应当少见。

##### 源码管理里怎么查

这份来源最可信，直接绑在代码上，也最完整。经过仓库的东西都应在这里。它包含提交历史、经 `gh` 看到的 PR 描述和评审讨论、行内注释、TODO、FIXME、弃用说明、仓库里的 ADR、测试、同一次提交里一起改的文件、CHANGELOG 和发布说明，以及提交和 PR 正文里提到的票据 ID。测试的名字和断言常常编码了推动改动的边界情况。

在种子提交之外继续扩。

```bash
git log --follow --oneline -- <file>
git log -S '<exact_string_from_code>' -- <file>
git log -G '<regex>' -- <file>
git blame -L <start>,<end> <file>
git show <hash>
git log <old>..<new> -p -- <file>
```

对每一次有实质内容的提交，用 `git log -1 --format=%B` 找 PR 号，再用 `gh pr view` 取正文、评审和链接的问题。`--json` 里的 reviews 和 comments 才是真正的信号。仓库里的 ADR 用对 `architecture decision` 的搜索来找。目标附近搜 TODO、FIXME、HACK、XXX、NOTE。相关测试用符号去配测试文件。

好证据是：PR 解释被解决的问题，而不只描述改动。一场辩论过替代方案的长评审。目标行附近解释了不明显约束的注释。名字暴露边界情况的测试。引用票据或事故 ID 的提交说明。写出用户可见理由的 CHANGELOG。

坑有这些。仓库若 squash 合并，分支上的个别提交会丢，退回到 PR 正文和评论。 “Small refactor” 有时藏着有意的行为变化，看 diff，不要只看说明。作者可能复制了一种自己也不懂的模式，去查这个模式更早从哪次提交来。Dependabot、Renovate 和自动回移植通常不携带动机，找意图时跳过它们。代码本身不是 “它为什么存在” 的证据。证据来自提交说明、PR、注释、测试和文档。不要把 “函数名叫 X” 当成意图的证据。

交回每一条相关的提交、PR 和评论。引用原文。带上哈希、PR 号或文件行。带上作者和日期。标明是直接回答了问题，还是旁证。

##### 票据里怎么查

Linear 这一类常常放着产品和业务上下文。 “因为客户 X 要求” 或 “这是第三季度合规计划的一部分”，在这里。内容包括功能与缺陷的动机、附在问题上的 PRD 或规格、父子问题、评论里的范围变化、标签、解释范围变化的状态更新、附件和链接的 GitHub PR。

用该类 MCP。先取种子提交或 PR 里已经点名的票据，读完整问题和评论。再用多种说法按关键字列相关问题。落到子问题时去取父问题。子问题是战术，父问题常常带着为什么。问题属于某个项目时，读项目和附带文档。标签暗示动机类别，例如客户要求、事故后续、合规。里程碑把工作绑到截止日期上，截止日期常常暴露动机。

好证据是写明业务问题的描述、记下决定的评论、像一项计划的父问题标题、附带的 PRD，以及 `customer`、`incident-followup`、`compliance`、`perf-regression` 这类标签。

坑有这些。PR 引用的票据可能关了又开，范围已经变了，要读完整历史。有的团队要求填 Why，填的却是套话，泛泛的 “改善用户体验” 多半不是真答案。旧票据常常反映已经变过的计划，对日期，并和代码的发布日期交叉核对。按 duplicate-of 追回那张规范票据。访问不到的问题记成缺口，不要猜。

每张相关票据交回 ID 和标题、从描述或评论里逐字引出的动机、标签、父问题、项目、作者、创建和关闭日期，以及能跳过去的链接。

##### 长文档里怎么查

长文档是为什么在变成代码之前的长篇形态。重要功能通常有一篇文档。内容包括 PRD、技术规格、RFC、ADR、设计评审的会议记录、领域背景、事故事后回顾、可能解释防御代码的 runbook，以及设定优先级的策略文档。

用该类 MCP。关键字搜索试功能名、目标代码里的符号和类名、作者名（设计文档常常先于代码）、错误字符串或用户可见的词，以及已知发布窗口时的时间范围。候选页读全文，不要只读预览。理由常常埋在文档中部。跟着反向链接和子页走。替代方案、附录和实现笔记常在子页。相关数据库和会议记录可以查出讨论过这个决定的笔记。PR 作者若有个人笔记本，里面可能有代码落地前的探索。

好证据是对得上目标用途的问题陈述、考虑过并否决的方案、把目标代码点名为某次事故修复的事后回顾、与 PR 作者和日期对得上的 “我们决定 X 因为 Y”、以及认真填过的 ADR。

坑有这些。规格常常写在实现之前，之后不更新，文档描述的计划可能已经变了，要和实际 PR 交叉核对。规格说做 X、代码做 Y 时，标出分歧。模板里的 Why 可能是空话，看它具体不具体。最相关的文档可能没有任何链接，宽关键字搜索有帮助。同一主题有多篇草稿时，找定稿或最近更新的那篇，看日期。访问不到的页面记成缺口。

每篇相关文档交回标题和 URL、作者和最后更新、逐字的动机及所在章节、相关链接页，以及它是定稿还是草稿。

##### 实时聊天里怎么查

较小的改动常常不配一篇文档，真正的决定在聊天里。它也最易逝。帖子会删，频道会归档，搜索质量会随时间变差。内容包括问题和决定的实时讨论、事故频道里的应急决定、权衡过的设计讨论、没有写进文档的资深工程师回答、合并之后解释为什么又回头看的讨论。私信通常搜不到，范围要按这个来。

工具因 MCP 而异。先看哪一个聊天 MCP 可用，并查看它的工具模式。它可能要求 `mcp_auth`。认证失败就停，并报告缺口。

搜索顺序是这些。先按 PR 作者、围着合并日期搜，范围会小很多。再按功能名和关键符号搜，包括拼写错误和随便的说法。搜 PR 的 URL，或只搜 `/pull/` 加号码。代码若处理某条错误，就搜那条错误字符串。再把范围收到可能的频道：`#eng-*`、`#proj-*`、`#incident-*`、`#sev-*`、拥有团队的频道、设计评审频道。找到相关消息后取整条线程。决定常常在回复里。

好证据是明确辩论过取舍的线程、描述这段代码所防止的缺陷的事故频道消息、评审者的问题和作者或负责人的回答、指向某次已做决定的会议，以及产品或面向客户的工程师解释的客户要求。

坑有这些。很旧的消息可能因保留政策消失。某个日期之前什么都找不到时，记下这道保留悬崖。许多决定发生在搜不到的私信里，这是已知限制。随便的玩笑不是决定，即使它出现在提交之前。单条消息脱离线程常常读错，始终取线程。MCP 没认证就停。不要编造发现。报告聊天无法搜索。

每条相关线程交回频道名、永久链接或线程 ID、参与者、讨论的日期范围、带归属的逐字引语，以及它属于哪条线程、哪次事故或哪场讨论。

##### 可观测性里怎么查

这一类是生产里实际发生过的记录，相对的是计划和讨论。指标的存在本身就是证据，有人认为这个数值得看。监视器和告警是团队决定值得把人叫醒的条件。仪表板是精心挑选的视图。APM 的追踪回答为什么慢、为什么这里有超时。日志常常含有推动防御代码的错误条件。事故记录带时间线和链接的事后回顾。笔记本是探索性调查。

用该类 MCP。先宽后窄。先识别拥有的服务和上下游。然后先看仪表板和监视器，它们告诉你团队在乎什么。覆盖到目标时，记下查询和被看着的阈值。阈值常常就是 “为什么钳在 N” 的答案。再看目标附近的指标，把轨迹和 PR 日期对上。一次尖峰紧挨着重试逻辑的合并，是强的支持性证据。日志要收窄，不要倾倒。优先用有时间边界的查询，例如改动前后各 30 天。不受约束的搜索又慢又可能超时。需要计数时做聚合，不要倾倒原始日志。追踪用于超时、重试、慢路径和跨服务行为。目标看起来是防御性的，就搜它被加进来那段时间的事故。时间线里写着 “为 X 加了防御检查” 的事故，接近直接证据。

好证据是查询和阈值与代码强制的约束相符的监视器、目标作者建的仪表板、合并前尖峰而合并后稳定的指标、引用目标代码或同样错误字符串的事故，以及改动前窗口里、防御代码会防止的那种错误日志。

坑有这些。相关不是因果。同一窗口里可能还有别的 PR，要查相邻的 PR。你找到的图是人做的，反映那个人的框定。一张叫重试成功率的图，说明团队在乎重试成功率，不等于某一行代码因此存在。指标会改名、删除，或保留期很短。相关窗口没有数据，是缺口，不是空结果。常见字符串会命中成千上万条日志，按服务、标签和时间狠狠收窄。被测量不等于被它引起。指标存在只说明有人在乎到去测量。和提交、PR 的日期交叉核对。

每一项交回类型、标题或名字、标识、所有者和日期、与问题相关的条件或原文，以及它暗示什么、连接有多强。

##### 错误跟踪里怎么查

这一类是出过错的档案。对防御、纠正或错误处理的代码，它常常握着直接动机：推动某人加上检查、捕获、重试或退路的具体异常、堆栈和频率。问题是分组后的错误，带计数、首次和末次出现、受影响的发布和评论。事件是单次实例。发布把部署和问题连起来。回放是面向用户的错误的会话记录。性能剖析对 “为什么” 用处较小。评论和指派有时有工程师写下的根因。

最有价值的是时间上的对照。问题在某天出现，峰值到每天数百次，在带上防御检查的那次发布之后停止。

用该类 MCP。不知道项目和组织时先定位它们。搜索用异常类名、目标的函数或类名、目标检查的错误字符串、目标的文件路径。再按发布和时间窗口收窄。看首次出现、末次出现是否对齐发布日期、哪些版本见过它、频率是尖峰后解决还是别的形状。拉完整事件，看堆栈是否经过目标代码，标签和面包屑是否符合目标所防御的条件。查靠近目标提交日期的发布，把版本和 PR 合并日期交叉核对。自动根因分析可以当假设发生器，当作推断，不当作权威。事件、堆栈和时间戳才是主要证据。

好证据是首次出现略早于 PR、末次出现略晚于 PR 的问题，经过目标函数的堆栈，PR 作者在问题上的评论，PR 或提交里引用的错误跟踪 URL，以及计数很高、在包含目标的那次发布后停止的问题。

坑有这些。分组按指纹。重构或改名会让 “同一个” 错误换成新的问题 ID。一个问题突然结束，可能只是被重新分组了，要查紧接着出现的新问题。一次发布含有许多提交。问题停在某个版本，不能证明是目标修的。错误停止也可能是上游变了。标成已解决可以是人手标记，没有代码改动。自动分析会生成听起来自信但并不对的解释。有的项目采样很狠，低计数可能只是高采样。拿不准时记下缺口。

每条相关问题交回 ID 和标题、项目和组织、首次和末次出现、事件计数和已知的采样率、受影响的发布、能看出和目标相关的堆栈摘录、与发布日期的对照、链接，以及作者评论或解决说明。

##### 产品分析仓库里怎么查

这一类补的是产品和数据视图。可观测性是基础设施和运行时。这里是用户做了什么、跑过哪些实验、功能使用怎样变化、某个阈值常量从哪来。内容包括产品分析事件、用量和计费事件、实验和功能旗标的表、系统表、dbt 血缘，以及笔记本。实验和旗标的表结构因公司而异，先用 `SHOW TABLES` 探，再假定名字。系统表回答查询贵不贵、有没有人经常跑、仓库负载何时尖峰。dbt 模型揭示哪些流水线依赖某张表或某个字段，上游变化常常推动消费方代码的变化。笔记本不能经 SQL MCP 查询。怀疑理由在笔记本里，就把它记成缺口。

主工具是只读执行 SQL。若返回 `statement_id`，用轮询取结果，不要重跑。查询之前先定向。表巨大，不受约束的扫描会超时。每条查询都加时间边界，事件用 `_timestamp`，查询历史用 `start_time`，窗口通常是发布日期前后各约 30 天。有强理由才放宽。优先用已经去重、有类型的 dbt 模型，不要用带重复和未定类型 JSON 的原始表。模型名对不上时用 `SHOW TABLES` 确认。只有还没有 dbt 模型，或需要刷新延迟之内的事件时，才退回原始表。类型化模型上常见的列包括 `_timestamp`、`_id`、事件名，以及 `properties_` 开头的事件属性。

往往值得做的调查有这些。发布前后约 30 天的每日计数。合并后一两天内从零跳到稳定用量，是功能随这次 PR 推出的有力旁证。衰减到零暗示弃用或删除。防御检查的来源，看 PR 之前 14 天里相关属性的中位数、p99 和最大值。p99 对得上代码里的阈值常量，暗示这个数是从数据里选的。实验或旗标先找到暴露表，再按变体拉接近 PR 日期的暴露计数。迁移、回填或性能重写，在查询历史里按语句文本和时间窗口找昂贵查询，按耗时或读取量排序。目标若读写某个分析模型，该模型自己的 git 历史常常带着理由。把这条线索交回 git 调查员，不要自己追。

好证据还有：分类错误的事件在防御性 PR 之后几天降到接近零。暴露表的一行点名了目标的旗标键，并在发布日期附近有 shipped 或 concluded 的决定。

坑有这些。被记录不等于被它引起。声称因果之前，配上 git 调查员的 PR 或提交引用。用量的阶跃可能是新事件开始被记录，不是用户行为变了。先查同一窗口里的埋点 PR。事件属性会演化。今天模型上的列，目标被写的时候可能还不存在。更老的数据可能只在原始 JSON 里。dbt 按计划重建，最近几小时退回原始表，并按 `_id` 去重。报告一张你从未确认存在的表，是典型失败。相关窗口早于保留期或模型创建日，是缺口，不是 “没有活动”。要明确命名，免得综合者把 “没有结果” 读成 “没有活动”。

每一项交回类型、完全限定的表名和实际跑的查询、时间窗口、紧凑的数字摘要。计数、分位数、首次和末次出现的时间戳。不要倾倒原始行。写下和发布日期的时间对照，以及强度是直接、旁证还是弱。

##### 事故与事后回顾

这不是单独的一类来源，是一个横切角度。事故常常推动防御代码。目标看起来是防御性的，就在每一个可用来源里专门找事故史。长文档里搜提到目标文件、功能或错误字符串的事后回顾。票据里找标了 incident、`sev-*`、事后行动项、可靠性的问题。聊天里在代码被加进来的日期附近搜事故频道。Git 里， “fix for incident”、 “add defensive check”，以及 revert 之后又 “re-apply” 的提交说明，是强信号。可观测性里搜正式事故记录，以及作为事后行动项建起来的仪表板和监视器。错误跟踪里看首次和末次出现是否对齐 PR 的发布日期，堆栈是否经过目标。产品分析里，给错误分类的事件常常在事故窗口尖峰。目标 PR 发布后计数下降，是目标解决了用户可见症状的旁证，即使另外两类信号很吵。

找到事故链接就取完整的事后回顾。事后回顾通常有 Action Items，直接绑到代码改动。多个来源互相印证时，证据尤其强。例如一个事故 ID 出现在票据里，票据出现在事后回顾里，事后回顾出现在链接到目标 PR 的聊天线程里，而错误事件的计数在修复后下降。代码看起来不像防御性的，就跳过这个角度。

##### 调查员怎样工作

调查员收集证据，不直接回答问题。综合者来称重量、下结论。其他调查员在并行搜不同来源。不要试图覆盖一切。在分到的来源里走深。

循环是这六步。

1. 先撒宽网，再收窄，以免错过相关上下文。
2. 整篇读完。PR、票据、文档或线程不要只读标题或摘要。关键证据常常埋在评论、子任务或后续里。
3. 跟上来源内部的链接。PR 指向另一个 PR 或提交，就取来。票据指向父项或同级，就取来。文档指向另一篇文档，就取来。留在分到的来源之内。看到跨来源的引用，不要自己追。记在 Additional Leads 里，让负责那个来源的调查员去取。一个调查员一类的设计靠这一点。追跨来源链接会重复劳动，也会弄乱范围。
4. 逐字抓住引语，带上位置。PR 号、票据 ID、URL、提交哈希或文件行。综合者需要精确引用。
5. 记下缺失。搜了却空，也是发现。记下搜了什么、没找到什么。
6. 留意矛盾。同一来源里两项不一致，两项都记。不要压下不方便的那一项。

不要综合，也不要形成 “为什么” 的最终意见。诚实、完整地收集原料。

纪律还有这些。不要把机制当成动机。把 `limit` 从 50 改成 100 的提交显示了变化，不一定显示为什么。解释在提交说明、PR 描述、链接的票据或评审评论里。不要从代码风格推断意图。 “作者选了函数式” 是对代码的观察，不是意图的证据。只有作者说出意图时才声称意图。证据含糊就说含糊。一种读法更说得通但不确定，就说不确定。不要为了显得决断而压扁含糊。问题关于功能 X，却只找到功能 Y 的证据时，不要把 Y 当成 X 的答案。不要发明。想把部分发现说圆成自信的陈述时，停下来，标成部分。

交回的结构是 Source、What I Searched、Direct Evidence Found、Indirect / Circumstantial Evidence、Contradictions、Gaps、Additional Leads。直接证据写它说了什么、从哪来、作者和日期、以及它怎样落到问题上。间接证据写它是什么、从哪来、谨慎的读者可能推断什么、以及另一种读法。矛盾要两条引用都在。缺口要具体到查询和时间范围。

调查员不做的事是写最终答案、在矛盾里选边、超出证据去推测，以及靠读代码来弄清意图。可以读代码以弄清目标是什么。不要把 “代码做什么” 和 “为什么” 混在一起。

#### 第 4 步，综合

派一个综合者。

- `subagent_type` 为 `generalPurpose`
- `model` 读 `why synthesizer` 那一行，默认 `claude-opus-5-5-max`
- `readonly` 为 `false`。质量检查会抽查引用，这可能需要 MCP。只读或 `Ask` 模式会剥掉 MCP，抽查就做不成。

综合者拿到调查员的发现，包括空结果和带理由跳过的类别。加上第 2 步的代码锚点、用户原来的问题、`references/epistemics.md` 的框架，以及 `references/synthesizer-prompt.md`。

综合者按信心加权，写出带引用的叙述，诚实说明证据支持什么、不支持什么。写之前读完认识论框架。规则是这些。每条主张落在 Direct、Supported、Inferred、Speculative、Unknown 之一。Direct 和 Supported 必须有引用，形式是 PR 号、票据 ID、文档 URL、聊天永久链接、提交哈希或文件行。Inferred 和 Speculative 必须用留余地的说法。绝不把代码引用成它自己意图的证据。证据的缺口必须写下来。用户问题里嵌着的假设当作候选，不当作结论。

做法是这些。读完全部发现。它们是原料，不是结论。多个调查员引用同一份 PR、票据或文档时，合并成一条权威引用。两项证据不一致时不要选一个，两个都摆出来。每条主张标出证据和层级。Direct 说清楚并引用。Inferred 留余地并解释推断。Speculative 明确标出。没有证据的放进缺口。抽查引用。可以读代码库、调用 MCP 工具来核对。不要写文件、不要提交、不要改外部状态。不确定某条被引用的东西是否存在、或是否真的那么说，就去查。不要传播错误。用户会按输出行动。把开放问题留着，好过用听起来自信的猜测填上。

输出用这个结构。可以按需要调整，但信心的分离要保持。Sources Consulted 每个调查员一行，包括什么都没返回的和被跳过的，并写上理由。

- The Question。用一两句重述用户的问题，让答案有锚。
- The Code in Question。文件路径、行范围、关键符号。两三行，让冷启动的读者能定向。
- What We Found。有直接证据的主张，一条一个项目。引用或转述来源，并精确引用。单来源的明确证据用 `[Direct]`。多条间接项汇合到一个结论时用 `[Supported]`。
- What We Can Reasonably Infer。没有地方明确写出、但被间接证据好好支持的主张。把推断链写可见。“Given A and B, it's likely that C.” 用 appears to、likely、suggests、is consistent with。每条标 `[Inferred]`。没有可推断的就删掉这一节。
- Competing Hypotheses。证据能套上多个故事时，把它们摆出来。记录不支持一个赢家时，不要硬选。每个假设写一句话、支持它的具体项、以及反对它或缺失的东西。只有一个清楚答案时删掉这一节。
- What We Don't Know。用户问了、证据没回答的事。搜了却空的来源。根本无法搜索的来源，例如缺少实时聊天 MCP。要具体。写上没有回答的具体问题、返回空的搜索、不可用的来源和原因，以及很可能知道但你问不到的人。
- Sources Consulted。实际搜过什么的项目列表，让用户判断覆盖并改口。源码管理写文件路径、看过的提交数、PR 号，以及搜过的代码注释。这一类没搜是不该发生的，因为 git 和 `gh` 始终被期望可用。其余六类各写搜了什么。没搜就写 Not searched，并写这个环境里没有匹配的 MCP。产品分析那一行还要写完全限定的表、时间窗口，以及和问题相关的数字摘要。
- Confidence Summary。一两句总的信心。例如核心理由有 PR 和票据的直接证据。某个阈值是从周围上下文推断的，没有明确文档。某个问题无法回答。某些来源没有内容，实时聊天搜索不可用。

交回前按七条检查。What We Found 的每一条都有引用，否则移走。措辞和层级相称。注意到的矛盾有没有摆出来，而不是悄悄选了一个。What We Don't Know 存在，并点名具体缺口。历史调查几乎总有缺口。空着或缺失就值得怀疑。用户嵌进问题的假设，是对照证据检查了，还是盖了章。有没有把代码引用成它自己意图的证据。整体语气是否校准。听起来自信、证据却弱，正是这个技能要防止的失败。任一条失败就先改再交回。

这份输出的价值在诚实，不在权威。读者拿着它去问原作者、工程负责人或产品经理时，应该能问对后续问题。写清已知、推断和缺失。不要为了看起来决断而优化。

#### 第 5 步，呈现

把综合者的输出交给用户。可以为清楚而轻改，或补上对话里的上下文。不要改写信心用语。

Sources Consulted 之后，若用户的 `why` 问题是改这段代码的前奏，把谱系发现转成一组约束，供计划改动使用。四项是 Preserve、Change、Avoid、Risk。

### 使用例

下面两条来自原文，不是本书自拟。第一条在指南里。第二条在 README 里。

```text
/why was the retry limit set to five? does the reason still hold?
```

```text
/why is this feature flag not on yet?
```

第一条同时问历史理由和这个理由现在是否还成立。重试上限看起来是防御性代码，调查员除了自己的类别说明，还应附上事故与事后回顾那份横切说明。第二条问的是一个还没打开的旗标，产品分析、票据和长文档都可能有迫使力量。两类都先做第 2 步的代码锚点，再按当时可用的 MCP 并行查询。

> **示例（本书作者所写，原文中没有）**
>
> `/why` 上传大小为什么钳在 100？我猜是为了性能。这个理由现在还成立吗？

代理应把 “为了性能” 当作一个候选，而不是结论。它先钉住钳制所在的文件、符号和最近的提交，再按可用 MCP 并行查七类。聊天或错误跟踪没有 MCP 时，在 Sources Consulted 里写成缺口。综合者保持 “appears to” 这一类说法。呈现时不把这些说法改写成 because。

### 陷阱与注意

最近一次提交不一定作数。当前形状常常是许多更早决定的堆积。要往回追。这是技能点名的失败模式。

只读或 `Ask` 模式会剥掉 MCP。调查员和综合者都要用 `agent` 模式。他们仍然不写文件、不提交、不改外部状态。

不要让一个代理包下多个 MCP。覆盖图要完整。空结果是发现。跳过只有两种合格理由，并且要写进 Sources Consulted。单提交就能在行内答完，必须先确认七类搜索都多余，并明确说出来。

代码不是它自己意图的证据。函数名、风格和 “它现在说得通” 都不是动机。

用户嵌进问题的假设不能直接证实。互相矛盾的票据和 PR 都要留下。缺口用具体的搜索来写，不用自信的猜测填上。

可观测性和错误跟踪里，时间上的前后是旁证。同一窗口的其他 PR、重新分组、上游变化、人手标记的 resolved、采样，都会把相关说成因果。产品分析里，阶跃可能是新埋点，保留期之外的空是缺口。聊天认证失败就停。自动根因分析是假设，不是主要证据。

squash 合并会抹掉分支提交。退回 PR 正文和评论。机器人提交通常不携带动机。
