# teach 与 recall：讲清楚与恢复上下文

[`how`](how.md#skill-how) 讲代码现在怎样运行。[`why`](why.md#skill-why) 追查它为什么长成这样。`/teach` 把两者织成一篇人能学进去的说明。`/recall` 在开始或接着做之前，从你自己的近期记录和共享记录里恢复当前上下文。指南把这四条放在改代码之前。摘要不够用时用 `/teach`。回到一个已经冷下来的题目时用 `/recall`。要接上某一段特定的先前对话，那是 Session pickup，不是 `/recall`。{{src:docs/guide/03-understand.md}}

## teach {#skill-teach}

原文：{{src:skills/teach/SKILL.md}} {{src:README.md}} {{src:docs/guide/03-understand.md}}

> 按对方的节奏，把一件东西是什么、怎样运作、为什么做成这样，讲成一篇清楚的说明，目标是理解，不是改动。

### 何时使用

触发说法是 “teach me this”、“help me really understand X”，以及把这次改动或这个子系统讲清楚。README 写的是：你想真正理解一次改动或一个子系统，而不是只拿到一份摘要。它运行 `how` 和 `why`，织成一篇清楚的说明，并且一张图一张图地搭起来。

指南的例子要求说明这个 PR 怎样改变重试，并说服你它修的是原因而不是症状。指南写明， “convince me” 这种框定值得借用。它把说明变成你可以戳的论证，而不是一次游览。小改动也许只跑 `how` 和 `why` 里的一个。{{src:docs/guide/03-understand.md}}

前置信息写着 `name: teach` 与 `disable-model-invocation: true`。技能正文没有解释后一项。

### 运作方式

`teach` 坐在 `how` 和 `why` 上面。先弄清这件工作是什么、它碰到什么。再跑 `how` 看它怎样运作，跑 `why` 看它为什么是这样。那是两次真正的技能调用，它们自己去挖。把找到的东西织成一篇平实的说明。先讲对这个人重要的部分。对方追问时再深入。为了教学可以自由改写，只有一条例外。保持 `why` 的信心用语原样。它的留余地是发现，不是文风。

每一则回复都经 [`unslop`](writing.md#skill-unslop) 来写。用平实的口头英语，像对同事解释。要紧，但不要干。砍掉垫词和含糊的退让，留下让它说通的那一部分。说出具体机制。不要比喻，不要框定，不要预告后面要讲什么。目标密度是这段英文。 “Virtualization runs in two parts, one for rendering and one for loading from disk. When an item scrolls out past the buffer, both its DOM node and its in-memory data are evicted.” 用正常的句式大小写，不要全小写。不用破折号。句号优先于逗号。一句里的逗号停在一到两个。从句堆起来就拆成独立的句子。每个概念只用一个名字，并保持这个名字。避开镜像句，原文的例子是 “A without B, or B without A”。避开整齐的收束，原文点名 “the rest follows” 和 “it all falls out”。这些步骤里的词是说给你的指示，不是要印出来的标签。不要把结构回声成标题或套话。

五步如下。

1. 决定对方离开时应该理解的少数几件事。从他们为什么问来选，也从他们已经知道什么来选。两者都从对话里读，不要考他们。他们即将改它、正在评审它、正在调试它，或是新来的，深度不一样。他们明显已经知道的就跳过。深度放在他们的问题上。
2. 让 `how` 和 `why` 做事，不要自己重做。自己读代码，只为了定向。然后跑 `how` 看怎样运作，跑 `why` 看为什么。两者并行，再合并结果。规模匹配问题。子系统两个都跑。小改动也许一个就够。默认把 `why` 收窄，因为它的完整扫查很慢。收窄写进对它的请求本身，例如一个有范围的问题，加上 git 和一两个来源。这样 `why` 会按它自己的约定记下被跳过的类别。只有理由本身就是要点时才放宽。
3. 从一句平实的定义开始。叫出这件东西的名字，用资深工程师会说出口的方式说明它一般是什么。有常用名就用常用名。然后绑到眼前的情况，原文的形状是 “in X, we use this to ...”，再从那里建起来。怎样运作，更深的理由，边界情况。每一部分都把想法讲到能说通。它解决什么问题，它实际上怎样工作。当对方做这件事时发生了什么，能让它落地，就按那个过程走。原文的例子是打开一长段聊天、再向上滚动。列出函数和常量是参考，不是教学。不要印这些框定标签： “the one idea to hold onto”、 “the thing to walk away with”、 “the key insight”、 “at its core”、 “TL;DR”。先给最小的完整答案，一两句，不是一段密文，然后停。对方问了再加层。不要一堵文字墙。
4. 保持对话，不要变成讲课或表演。提出可以再深入或继续往前，然后跟着对方。不要测验。不要把节奏演成一场戏。不要印 “Pause”。不要请他们复述。不要宣布 “the sentence to nail”。不要把某一段标成重要或难，原文点名不要说 “here is the part worth slowing down on”、 “this is the tricky part”、 “here is where it gets interesting”。直接说。你本会停下来的地方，就停下来让他们回应。一次性运行、没有现场的人时，干净地交出来，把可以再深入的提议放在末尾。
5. 不要只说，要给看，并且一张图一张图地把画面搭起来。diff、代码或调试器是最快落地的方式时，就打开它。一张图比话更快时，就画。有三个或更多活动部分时，不要一次画进所有部分。画短的一系列。每一张重画上一张，并只加一个部分，让读者看着系统装起来。一张一次画完的图，尤其是留到最后的那张，是参考，不是教学。具体地说，要教从 A 到 B 到 C 的流程，就画三次。先是 A 到 B。然后重画并加上 C。然后重画并加上返回边或下一块。介质匹配想法。两种都有帮助时两种都用。流程或结构、标签本身承载意义时，用 mermaid。想法是空间的，例如布局、重叠、滚动位置，或前后对比，就用图像生成工具，画成白板上的记号笔，只加几个短标签。图像模型会把长文字画乱。把那张图生成出来，不要停在用话描述它。搭起来的规则对生成的图同样成立。一个简单的点不需要图。

回复就是说明本身，绝不是一份关于你做了什么、交付了什么的报告。先说要点。然后是它是什么、怎样运作、为什么的平实叙述。再加上值得用 `how` 或 `why` 继续追的线头。

### 使用例

下面这条来自指南，不是本书自拟。

```text
/teach me how this PR changes retries. convince me it fixes the cause and not the symptom.
```

代理先从对话里判断对方要理解的是这次 PR，而且对方要的是原因而不是症状。它定向地读代码，并行跑 `how` 和 `why`。这是一次改动，也许一边就够。若理由就是要点，就把 `why` 放宽。说明从一句定义开始，用一张接一张的图搭起重试的流程。`why` 带回的 appears、likely 一类说法保持原样。回复本身是说明，末尾可以提出再深入。

> **示例（本书作者所写，原文中没有）**
>
> `/teach` 我刚接手通知去重。先用两三句告诉我它在防止什么，再按我打开一条长列表时实际发生的步骤往下讲。

这是新人接手一个子系统。深度放在 “打开长列表时发生什么”。对方还没问的历史理由先不铺开。`why` 若要跑，请求里就把它收窄。

### 陷阱与注意

不要重做 `how` 和 `why` 已经挖过的工作。教学上的改写是自由的，`why` 的信心用语除外。把 likely 改写成 because，会把发现变成文风。

默认收窄 `why`。完整扫查很慢。收窄要写进请求，让 `why` 按它自己的约定记下跳过的类别。理由本身就是要点时才放宽。

函数和常量的清单不是教学。一次画完的总图是参考。三个或更多活动部分要分成一系列，每张只加一块。

不要印框定标签，不要测验，不要宣布这里很重要或很难。一次性、没有现场的人时，干净地交付，把再深入的提议放在末尾。

回复不是工作报告。先说要点。

### 相关技能

- [`how`](how.md#skill-how) 与 [`why`](why.md#skill-why)。本技能调用它们，不代替它们。
- [`unslop`](writing.md#skill-unslop)。每一则回复都按它来写。
- [`recall`](#skill-recall)。恢复的是你自己的近期上下文，不是把子系统讲通。
- [`poteto-mode`](poteto-mode.md#skill-poteto-mode)。README 列出模式会在步骤里调用的技能时，没有把 `teach` 算进去。想学进去时直接点名 `/teach`。{{src:README.md}}

## recall {#skill-recall}

原文：{{src:skills/recall/SKILL.md}} {{src:README.md}} {{src:docs/guide/03-understand.md}}

> 开始或接着做之前，重建近期工作上下文，交回一份当前状态和下一步的简短摘要。

### 何时使用

触发说法是 “recall my work on X”、 “catch me up”、 “what have I been working on”、 “where did I leave off”，以及开始或恢复工作之前。

README 写的是：你正在开始或恢复工作，希望围绕一个题目，从你自己的聊天历史和共享记录重建近期上下文，并交回一份紧的当前状态简报。

指南的例子是赶上上周的导出工作。回到一个已经冷下来的题目时用它。若要恢复某一段特定的先前聊天，那是 Session pickup，不是本技能。{{src:docs/guide/03-understand.md}}

前置信息写着 `name: recall` 与 `disable-model-invocation: true`。技能正文没有解释后一项。

### 运作方式

保持紧，并停在题目上。只读范围内的线程需要的东西，然后停。

上下文在两份记录里。你自己的聊天历史放着你做了什么、决定了什么。共享记录放着同一段代码在其他名字下发生的事。用户一直在报告的症状、已经发布又被回退的修复、生产里仍在报的错误。第二份记录就是 `why` 所搜索的。开篇点名的范围是源码管理、问题跟踪、聊天和问题频道、长文档，以及错误跟踪。一条功能若拖着长长的缺陷尾巴，故事大多在那里。不要只从你的转录重建它。

转录在 `~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl`。`<slug>` 是工作区路径去掉开头的斜杠，再把每个 “/” 换成 “-”。原文的例子是 `/Users/you/proj` 变成 `Users-you-proj`。每一行是一条聊天消息。

1. 先分类，再路由。要恢复的是某一段特定的先前聊天，那是 `session-pickup` 剧本，不是本技能。把习惯收成一个耐久技能，是 `automate-me`。把工作写成给人读的总结，是另一件事。本技能在你行动之前，跨近期聊天装入工作上下文。用户已经给了完整的状态摘要，包括路径、分支和改动，就用它，跳过挖掘。
2. 搜索之前先锁范围。钉住窗口。 “recent” 是一个真实的范围，默认最近 7 天。若点名了题目，就钉住题目。钉住工作区，默认是当前这个。没有被要求时，绝不读另一个项目的转录。把范围说回去。绝不要悄悄把 “all” 收成 “recent N”。
3. 在聊天历史上扇出。用一个快而便宜的模型并行派出子代理，每个拿走语料的一片。告诉每个子代理：候选按真实修改时间排序，用 `ls -t`，绝不按 UUID 名字排。先按题目 grep，然后只读匹配的聊天，并且只读相关区域。跳过当前聊天，以及明显的噪音，包括子代理聊天、eval 聊天和测试聊天。每个子代理交回同一套结构，一次聊天一块：题目、用户的目标、决定、开放的线头、挣扎和纠正、产物。产物包括 PR、票据和分支。每一项引用聊天 UUID。只有一两次聊天时，跳过扇出，直接搜。原始转录留在子代理里。主线程只拿到它们的发现。
4. 只要题目点名了功能、文件、子系统、区域或缺陷，就扫共享记录。这是默认，不是一项判断。 “my work on X” 也不能豁免。把它交给 `why` 的按来源调查员，但把他们的问题从 “为什么建成这样” 转成 “当前状态是什么、试过什么又没站住、用户还在报告什么”。复用它的按来源说明。调查员和聊天历史的挖掘并行。继承它的姿态。一个来源一个调查员。空结果是发现。不可用的 MCP 跳过并说明。把返回的东西折进简报。只有纯粹的活动回忆、没有点名目标时才跳过这一步。 “what did I do this week” 就是这种。那时你自己的历史和现场状态就是全部答案。
5. 对照现场状态核对。把挖掘和扫查露出的 PR、分支和票据，用 `git` 和 `gh` 检查。答案取决于某个代理实际做了什么时，包括它跑过的工具、读过的文件、碰到的错误，就读完整转录，不要只读一份裁过的本地副本。
6. 按下面的契约写简报。按线程分组。停在点名的题目上。

输出契约是这些。先是摘要，然后是线程状态，然后是问题，然后是下一步。更深的细节放在下面，或直接砍掉。

- Capsule。最多 5 条。这件工作是什么，整体停在哪里。
- Threads。每条一行，而且恰好一个状态标签。标签只能是 `[merged #N]`、`[open PR #N]`、`[in flight <branch>]`、`[verified, uncommitted]`、`[reverted #N]`、`[planned, not started]`。没有标签的线程还没写完，所以要给它标签。
- Problems。最多 5 条，要那些反复出现的。包括用户一直在报告的症状，以及已经发布又被回退的修复。下一次尝试从上次失败的地方开始。
- Next move。一个最有用的下一步，要具体。

相邻的功能或票据留在外面，除非它挡住这一件。摘要和线程行超出一屏时，先砍细节，再考虑砍线程。简报经 `unslop` 来写。聊天发现按 UUID 引用。共享记录的发现按它们的来源引用，包括 PR 号、票据 ID、聊天永久链接、错误跟踪的问题。任何公开输出之前，先清掉私人上下文。

回复就是这份简报，按上面的契约。

### 使用例

下面这条来自指南，不是本书自拟。

```text
/recall catch me up on the export work from last week
```

题目是导出工作，窗口是上周。这不是 “我这周做了什么” 那种没有目标的活动回忆，所以共享记录要扫。聊天挖掘和 `why` 的调查员并行。简报按线程打上状态标签，问题里包括仍在报告的症状和已经回退的修复，并给出一个下一步。

下面这条也来自指南。它不是 `/recall`。它走 Session pickup。先前的轨迹被视为权威。它重建分支状态和决定，点名续上的位置，并对照原来的目标核对继承来的说法，而不是从头把一切再推一遍。{{src:docs/guide/03-understand.md}}

```text
/poteto-mode take over this branch. read the decision log, figure out what's done, and continue from there. don't redo finished work.
```

> **示例（本书作者所写，原文中没有）**
>
> `/recall` 我这周都做了什么？先不要扫票据和聊天频道。

这是没有点名目标的活动回忆。按第 4 步，跳过共享记录。窗口默认最近 7 天，并把这个范围说回去。用户若说的是全部，不能悄悄收成最近若干条。

### 陷阱与注意

某一段特定的先前聊天，走 [Session pickup](playbooks-long.md#playbook-session-pickup)，不走本技能。把习惯收成耐久技能，走 `automate-me`。给人读的总结是另一件事。用户已经给了路径、分支和改动，就用那份摘要，不再挖掘。

范围先说回去。 “all” 不能悄悄变成 “recent N”。默认窗口是最近 7 天。没有被要求时不读别的项目的转录。

候选按 `ls -t` 的修改时间排，不按 UUID 名字排。跳过当前聊天和子代理、eval、测试聊天。一两次聊天不扇出。原始转录留在子代理里。

点名了功能、文件、子系统、区域或缺陷，共享记录就是默认，即使用户说的是 “my work on X”。只有 “what did I do this week” 这种没有目标的活动回忆才跳过。调查员的问题要改成当前状态、没站住的尝试、仍在报告的症状。空的 MCP 要说明。

答案取决于代理实际做了什么时，读完整转录。PR、分支和票据用 `git` 和 `gh` 核对。

没有状态标签的线程还没写完。相邻事项除非挡住这一件，否则不写进来。超出一屏时先砍细节。公开之前清掉私人上下文。
