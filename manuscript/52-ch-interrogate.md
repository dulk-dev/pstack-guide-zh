# interrogate：多个模型尝试拆掉 diff

多个审阅者各自挑战同一份改动。对抗性来自模型不同，不来自指定的人格。每个模型拿到同一份提示和同一份量规。交付的是综合裁决。不要自动应用修改。

## interrogate {#skill-interrogate}

原文：{{src:skills/interrogate/SKILL.md}} {{src:skills/interrogate/references/reviewer-prompt.md}} {{src:skills/interrogate/references/rubric.md}} {{src:skills/interrogate/references/code-quality-review.md}} {{src:skills/interrogate/references/lead-judgment.md}} {{src:docs/guide/04-design.md}} {{src:docs/guide/10-recipes-and-pitfalls.md}}

> 按配置的模型各派一名审阅者，从各自的角度对抗式审查代码改动，再由牵头人合成裁决。

### 何时使用

触发说法包括 “interrogate”、“adversarial review”、“multi-model review”、“challenge this”、“stress test this code”、“find blind spots”、“tear this apart”。

`name` 是 `interrogate`。前置信息含 `disable-model-invocation: true`。正文没有定义这项。

[poteto-mode](poteto-mode.md#skill-poteto-mode) 的不可协商项写明，有争议的设计在交付前走本技能，并注明它是多模型对抗。README 写明，你有一份 diff，想让几个不同的模型试着拆掉它，其中包含严格的代码质量镜头。

指南 {{src:docs/guide/04-design.md}} 的阶梯是：一份已经做完、你仍不放心的小改动，只需要 `/interrogate`。昂贵且难回头的有争议设计，先 `/architect`，交付前再 `/interrogate`。该页写明 `/poteto-mode` 已经在用这架阶梯。你直接调用，多半是因为你想要比默认更多或更少的审视。

[Feature](playbooks-work.md#playbook-feature) 第 7 步：设计有争议时，交付前走 `interrogate`。

### 运作方式

#### 第 1 步，确定范围

从上下文认出要审查什么。

- 用户指向具体文件或一份 diff，就用那一份。
- 人在功能分支上，就跑 `git diff main...HEAD`，或相对合适的基线分支，取完整变更集。
- 用户的消息指向最近的工作，就收集相关文件。

把 diff 或文件内容，加上审阅者看懂代码所需的周围上下文，打成一包。

#### 第 2 步，写明意图

派出审阅者之前，把意图写成明确的一段。材料来自用户的消息、提交说明、若有的 PR 描述，以及代码本身。拿不准意图时，先问用户，再继续。

#### 第 3 步，派出审阅者

在同一条消息里用 Task 工具把审阅者全部派出。读 `~/.cursor/rules/pstack-models.mdc` 里的 `interrogate reviewers` 那一行，每个条目一名审阅者。下面的 Reviewer A、B、C 标签按配置的条目数加长或缩短。规则或那一行缺失时，用下表的默认值。

| 子代理 | 默认模型 |
| --- | --- |
| Reviewer A | `claude-opus-5-5-max` |
| Reviewer B | `gpt-5.6-sol-max` |
| Reviewer C | `grok-4.7-xhigh-fast` |

每名审阅者：

- `subagent_type` 是 `generalPurpose`。
- `model` 是配置的 `interrogate reviewers` 条目。没有配置行时，用表里的默认。条目是 `auto` 或 `inherit-parent` 时，省略 `model`，让这名审阅者跑在父级模型上。
- `readonly` 是 `true`。

Task 工具拒绝某个已配置条目时，让这名审阅者改跑它所属族的表默认，并说明这一点。族按前缀分：`claude-*`、`gpt-*`、`grok-*`。对不上族时，用 Reviewer A 的默认。表默认也被拒绝时，看错误信息里的有效 slug，选最接近的等价项，优先同一族里推理档最高的，用它派出，并另开一个 PR 去更新默认表。不要因为 slug 问题挡住这次审查。不要把别名条目当成被拒绝的 slug，也不要对它使用这两种回退。

读 {{src:skills/interrogate/references/reviewer-prompt.md}}，把模板填上四样东西：第 2 步写下的意图、diff 或文件内容、{{src:skills/interrogate/references/rubric.md}} 的量规、{{src:skills/interrogate/references/code-quality-review.md}} 的代码质量镜头。填好的同一份模板发给所有审阅者，所以每个模型都使用代码质量镜头。

审阅者提示的要点：你是对抗式代码审阅者，要找真实问题，包括缺陷、设计缺陷、安全问题和可维护性。你不是来帮忙或鼓劲的。意图那一段假定目标正确，审查执行是否很好地达成它。不要质疑意图本身。只使用用得上的镜头。简单的缺陷修复不需要大段讨论架构完整性。每条发现包含：

- **严重程度。** `critical`、`warning` 或 `nit`。`critical` 会造成缺陷、数据丢失、安全问题，或根本坏掉的行为。`warning` 是设计隐患、可维护性风险，或眼下还没立刻坏、但以后会痛的正确性问题。`nit` 是风格、命名和小改进。
- **发现。** 用具体说法写问题在哪，并指向具体行或函数。
- **证据。** 为什么这是问题。给出推理，不要只断言。
- **建议。** 可选。有具体替代方案才写。没有清楚的修法就跳过。

好的发现指向具体代码，说明为什么是问题，分清“这是坏的”和“我会换成另一种做法”，并考虑已经写明的意图。不要复述代码却不指出问题。不要表扬。没有问题就说 “no findings” 并停止。空的审查是合法结果。输出是结构化列表。每条有短标题、`Location`、`Finding`、`Evidence`，以及可选的 `Suggestion`。

量规 {{src:skills/interrogate/references/rubric.md}} 说，用得上哪些镜头就用哪些，不是每次改动都要全用。各镜头的检查点如下。

**Correctness。** 代码是否真的做了意图所说的事。边缘情况包括空输入、nil 或 `undefined`、边界值、并发访问。错误是被捕获、传播，还是被默默吞掉。差一、类型强制、整数溢出、字符串编码。状态管理里的竞态、过期闭包、悬挂引用。顺利路径和失败路径是否都成立。幂等：跑两次，或上一次跑到一半崩溃，会发生什么。答案若是“取决于留下了什么状态”，就缺一个收敛步骤。并发：多个参与者能碰到同一块可变状态（文件、分支、共享数据）时，访问是靠结构串行（锁、分阶段、独占所有权），还是靠守不住的约定。发现潜在缺陷时，要追执行路径。不要只标“这可能是 nil”，要写出让它变成 nil 的调用链。

**Root Causes vs. Symptoms。** 代码是在修真正的问题，还是在盖住症状。这通常要看改变文件以外的地方。读周围代码（调用方、被调用方、类型定义、兄弟模块），理解改动所处的架构。用 Read、Grep、Glob 跟着调用链走，读类型，先弄清代码为什么存在，再判断改动是否打在正确的一层。要看的东西包括：掩盖更深不变量被破坏的守卫子句，藏住破裂契约的重试，用类型转换压住建模错误。看见权宜做法就问为什么需要它，以及正当的修复长什么样。模块 A 里的修复，其实应该是模块 B 的契约。用说明去代替结构时，例如一条注释写着“不要做 X”，或一条靠人记住的约定，要问它能不能变成类型约束、lint，或让错误无法发生的运行时检查。

**Structural Integrity。** 代码是否合得进它所在的系统。边界上的纪律：校验是在系统边界，还是散在业务逻辑里。数据在进入系统时校验一次，内部就信任它。抽象层次：高层编排是否和低层细节混在一起。耦合：这次改动是否引入会让以后更难改的依赖。数据模型是否符合真实的访问方式。对的结构让下游代码变得明显，错的结构处处跟你作对。是接到旧设计上，还是读起来像设计从一开始就考虑了它。新需求若从一开始就知道，代码还会是这样吗。遗留双路径：是否在保留旧 API 的同时引入新 API。没有外部消费者时，在同一波里迁移调用方并删掉旧路径。不要留下会变成永久的兼容层。不要因为简单代码缺少抽象而扣分。过早的抽象比重复更糟。

**Verification。** 只读代码时，能否看出它能工作。有没有测试。测试的是行为还是实现细节。有没有能抓住回归的断言或不变量。这若是缺陷修复，有没有针对该缺陷的测试。这若碰到集成边界，整条路径有没有测到。检查真实的东西，不要检查代理。用文件 mtime 或缓存状态代替读取真实值，就是检查上的缺口。委托或异步工作：代码是在核对真实的输出产物，还是信任自我报告和摘要。

**Complexity Budget。** 复杂度是否配得上代码做成的事。可以更简单而不损失正确性或清晰性的代码。只服务一个调用点的抽象。为还不存在的情况准备的配置或参数化。死代码、无用导入、残留参数。没有当前调用方的“以防万一”路径。迁移已经完成，却为了不再需要的过渡稳定而留着的过时兼容路径。用户体验是否配得上这些复杂度。每个功能、控件和选项都要挣到自己的位置。做了一半的功能比缺少更糟。更简单更好，除非更简单是错的。三行重复好过过早的抽象。

**Security。** 每条安全发现都要追输入在代码里的路径并展示出来。用户输入未经清理就进到危险的汇（SQL、shell、eval、`innerHTML`）。新端点上的认证或授权缺口。代码、日志或错误信息里的秘密。安全关键路径上的 TOCTOU，也就是检查时刻与使用时刻不一致。

代码质量镜头 {{src:skills/interrogate/references/code-quality-review.md}} 是加在量规上的严格标准，关注实现质量、可维护性、抽象质量和代码库健康。它要求对结构有野心。不要只找局部清理。主动寻找 `code judo`：行为保持不变，实现却明显更简单、更小、更直接、更优雅的重排。

核心提示要求对当前分支的改动做深入的代码质量审计，重新想结构和实现，在不影响行为的前提下实质改善质量。改善抽象和模块性，减少面条代码，提高简练和可读。有清楚的改进路径、即使要重排一部分代码库，也去做。极其彻底。量两次，切一次。

七条维度，用得上的才用。

0. **对结构简化有野心。** 不要停在“可以再干净一点”。寻找能让整段分支、辅助函数、模式、条件或层次消失的重新框定。假定常常存在一步 `code judo`。它更有效地使用现有架构，让改动明显更简单。能删掉复杂度，就不要只把它重新摆放。
1. **不要让一个 PR 把文件从不到 1000 行推到超过 1000 行，除非理由非常强。** 把这当成浓重的气味。优先抽出辅助函数、子组件或模块。diff 跨过这条线时，先问代码是否应该先拆开。只有结果文件仍然明显有组织、而且有结构上的强理由，才可以豁免。
2. **不要让已有代码长出更多面条。** 怀疑新的即兴条件、散落的特殊情况，或插进无关流程的一次性分支。把“随机位置上的古怪 if”当成设计问题，不是风格上的小挑剔。把逻辑推进专门的辅助函数、状态机或模块，不要缠住已有路径。
3. **偏向清理设计，不要只因为能跑就接受。** 行为可以不变、结构却能明显更干净时，推向更干净的版本。优先去掉活动零件的简化，而不是把同一份复杂度摊开的重构。
4. **优先直接、乏味、可维护的代码，而不是取巧或有魔法的代码。** 把脆弱、即兴或“魔法”行为当成问题。怀疑那些藏起简单数据形状假设的通用机制。标出薄抽象、恒等包装，以及只加间接、不换来清晰的透传辅助函数。
5. **类型和边界的干净程度影响可维护性时，就要推。** 更清楚的类型边界可以存在时，质疑不必要的可选、`unknown`、`any` 或堆满转换的代码。优先显式的有类型模型，而不是形状松散的即兴对象。一条分支靠静默回退来盖住不清楚的不变量时，问边界是否应该写成显式的。
6. **逻辑留在正典的那一层，并复用已有辅助函数。** 指出漏进共享路径的功能逻辑，或从 API 漏出的实现细节。优先已有的正典工具，而不是一次性的私货。把代码推向正确的包、服务或模块，不要把漂移当成正常。
7. **不必要的串行编排和非原子更新，在更干净的结构已经明显时，算设计气味。** 独立的工作没有理由被串行时，问它是否应该并行。相关更新可能留下做了一半的状态时，推向更原子的结构。不要过度追究微优化，但要标出那些让代码更脆的、可避免的编排复杂度。

输出时的优先级：先是结构上的质量退步和错过的简化，然后是面条和分支复杂度，然后是边界、类型和文件大小，然后是较小的模块性与可读性问题。

批准线：不要仅仅因为行为看起来正确就批准。下列情况默认是阻挡项，除非作者能说明理由。PR 留着大量附带复杂度，而一步 `code judo` 本可以删掉它。把文件从 1000 行以下推到 1000 行以上。加入把已有流程缠住的即兴分支。把功能检查散在共享代码里。加入不必要的抽象、包装或堆满转换的契约，或者在已有明确正典归宿时重复已有辅助函数，或把逻辑放错层。这些条件没有满足时，留下明确、可执行的反馈，并推向更干净的拆分。

语气直接、严肃，对质量要求高。不要粗鲁，也不要把重大的可维护性问题说成温和建议。代码正在把代码库弄乱，就这么说。实现错过了明显的大幅简化，也这么说。真正的问题是结构时，不要满足于“也许改个名字”。

#### 第 4 步，综合

结果回来之后，拼成一幅图。

1. 解析所有审阅者的发现。
2. 认出共识。两个或更多模型独立提出的发现，信号最高。
3. 认出只有一个模型提出的发现。仍然值得读，但按这个分量来看。
4. 去重。不同模型可能用不同说法描述同一问题。合并它们，并记下哪些模型提出了它。
5. 记下分歧。一个模型标出某事，另一个明确说相反，这对裁决是有用的上下文。

#### 第 5 步，牵头判断

你是牵头审阅者，一名务实的资深工程师，不是中立的汇总器。完整框架在 {{src:skills/interrogate/references/lead-judgment.md}}。

把每条发现放进这些桶：

- **Act on。** 按实际目标，影响正确性、安全或可维护性的真实问题。它们会挡住一个真实的 PR。
- **Consider。** 论点成立，但你不确定现在就处理是否值得那个代价。值得用户注意。
- **Noted。** 技术上成立，但无法行动。依赖上下文、过早优化，或按当前阶段影响很低。
- **Dismissed。** 错了、吹毛求疵，或缺少上下文。简短说明为什么。

每条发现写明哪些模型提出了它、类别，以及一行分类理由。

牵头这一步存在，是因为对抗式审阅者有用在于他们凶。没有上下文的凶会制造噪音。审阅者只看到代码库的一片，以及一段意图。他们不知道已经试过并否决了什么，代码之外有什么约束（时间、依赖、迁移计划），哪些是临时脚手架、哪些是永久架构，栈里的下一个 PR 会处理什么。你有完整对话。用它。

过滤时按这些原则。

- **挑剔会膨胀。** 审阅者，尤其是对抗式的，倾向于把评审写满。找不到关键问题时，他们会把小挑剔写大来填空。若某人的发现全是挑剔和风格偏好，代码多半没问题。应当直接这么说。
- **假设与实际。** “要是有人在这里传入 null 呢”只有在调用方真的能传入 null 时才算发现。追到调用点。输入在上游已校验，或类型系统阻止了它，就驳回。只看着 diff 工作的审阅者不一定看得到整条调用链。你看得到。
- **过早抽象的警告。** 审阅者常建议抽出函数、加接口或制造抽象。这段代码需要以第二种方式变化吗。不需要的话，抽象就是过早的。能用的简单内联代码，好过对当前范围来说过剩的干净抽象。
- **“我会换成另一种做法”。** 这是代码审查里最常见的假阳性。一条发现若只等于“我更喜欢另一种做法”，它就不是缺陷，不是设计缺陷，也不可行动，除非审阅者指出当前做法的具体问题。驳回它们，并说明为什么。
- **缺少上下文的信号。** 建议去改作者没有写、也没有改的代码。标出与代码库其余部分一致的模式，只是审阅者不知道。推荐与你知道的约束冲突的做法。这些是信息有限时的诚实错误。得体地驳回。

审阅者说得对时，不要因为不舒服就驳回。对抗式审查的意义就是抓住你会漏掉的东西。值得注意的信号：多个模型独立标出同一问题。发现指出具体执行路径，不是假设。发现露出你对代码的心理模型有缺口。你读完觉得确实如此。对安全发现和正确性缺陷要特别小心。即使只有一个模型提出，也要多用审视。

好的裁决有用，不求面面俱到。用户应当能读完 Act on，修掉那些问题，然后有把握地交付。Act on 超过 5 条，多半是过滤得不够狠。Dismissed 不是凑数。它是信任机制。让用户看见你驳回了什么、为什么，他们就能在不同意的地方推翻你的判断。这比藏起被驳回的发现更有价值。

### 输出格式

裁决用这个结构。

- **Intent。** 引用第 2 步写下的意图段。
- **Reviewers。** 每名审阅者一条：标签、模型名、发现条数。
- **Act On。** 应当处理的发现。每条写描述、哪些模型提出、为什么要紧。
- **Consider。** 值得想的发现。每条写描述、哪些模型提出、涉及的权衡。
- **Noted。** 成立但优先级低。简短列出。
- **Dismissed。** 驳回的发现，附简短理由。
- **Agreement Map。** 模型在哪里一致，在哪里分歧，这种一致或分歧的图案说明什么。

```text
/interrogate review this pr.
```

```text
/interrogate the whole branch, but skeptically. no nitpicks unless it's an actual bug or regression.
```

```text
/interrogate the whole branch, but skeptically. don't change anything yet. no nitpicks unless it's an actual bug or regression in behavior.
```

配方页写明，这些限定词在起作用。“don't change anything yet” 让它保持只读。挑剔规则事先滤掉噪音，使 Act on 里的发现值得花时间。该页还写明，牵头人是务实的资深工程师，不是神谕，你可以推翻它。驳回的部分也要读。

按技能正文，回来的是综合裁决，不会自动改代码。

### 陷阱与注意

- 不要自动应用修改。
- 意图拿不准就先问，不要带着含糊意图派出。
- 同一份填好的模板发给所有人。不要给不同模型指派不同人格。
- `subagent_type` 用 `generalPurpose`。模式写明，`interrogate` 自己规定 `subagent_type`，用于多样模型的评审。不要改成 `poteto-agent`。
- 别名条目不是被拒绝的 slug。不要对它使用回退。
- slug 被拒绝时，另开 PR 更新默认表，不要挡住这次审查。
- Act on 超过 5 条时，先怀疑过滤不够，不要把清单当成更严格。
- 安全发现和正确性缺陷，即使来自单一模型，也要多用审视。
- 空审查是合法结果。没有问题就说 “no findings”。
